# choi-ugoki
運動を始めるハードルを下げるアプリ

## サービス概要

このアプリは、勤務時間が不規則だったり帰宅が遅かったりして、運動したいと思っても始められない人に向けたアプリです。小さな運動タスクを提案し、ユーザー自身もタスクを登録できるようにすることで、運動内容を考える手間と始めるハードルを下げます。

## アイデアのきっかけ

### きっかけとなった体験

妻はホテルで勤務しており、朝6時に出勤する日もあれば、帰宅が23時を過ぎる日もあるなど、勤務時間に大きな幅があります。私自身も飲食店で働いていて、帰宅が23時頃になることがあります。

健康のために運動したいと思っていても、遅い時間に疲れて帰宅すると、運動する気力が残っていないこともあり、何をするか考えることさえ面倒に感じやすく、結局何もできなかったりします。こうした状況を変えるために、疲れていても取り組みやすい小さな運動を提案するアプリを考えました。

### なぜそれが気になったのか

運動する意欲があっても、始める前に内容を考えたり、まとまった時間や努力が必要だと感じたりすると、最初の一歩が重くなることがあります。そこで、運動内容を考える手間と、実行する負担の両方を小さくできないかと考えました。

## 解決したい課題

### 表に見えている困りごと

勤務時間が不規則だったり帰宅が遅くなったりすると、疲れた状態で運動内容を考え、実行することを負担に感じます。その結果、運動したい気持ちがあっても何もできず、動画を見て一日が終わることがあります。

### 本当に解決したい課題

- **なぜ運動を始められないのか？** 疲れているときに、運動内容を考えて実行するのが負担だから。
- **なぜそれが負担なのか？** 運動にはまとまった時間や努力が必要だと感じるから。
- **なぜその考えが問題なのか？** 始める前に負担を感じ、行動に移せないから。

**本当に解決したい課題：運動を始めたい人が、疲れているときでも行動を選びやすくし、最初の一歩を踏み出すハードルを下げること。**

## 想定ユーザー

- **年齢：** 現時点では限定しない
- **生活・状況：** 勤務時間が不規則、または帰宅が遅くなりやすい仕事をしている。帰宅後は疲れていて、運動内容を考える余裕がない
- **環境：** 自宅で、ジムや専用器具を使わずに短時間でできる運動から始めたい
- **最初に使ってくれそうな人：** ホテル勤務で出勤・帰宅時間に幅がある妻

最も近いユーザーは身近な妻です。妻の勤務時間や帰宅時間に幅があり、疲れて帰宅した後に運動を始める難しさを身近で感じています。また、私自身も飲食店勤務で帰宅が遅くなることがあり、運動内容を考えることさえ面倒に感じる状況を共有しています。

## 利用イメージ

1. 帰宅後、運動したいが何をすればよいかわからず、アプリを開く
2. 今日のおすすめタスクを確認する
3. おすすめを実行するか、別の候補を選ぶ
4. 実行後、「できた」を記録する
5. 過去の記録や今週の達成回数を振り返る

小さなタスクをすぐに確認でき、自分の達成を振り返れることを継続利用のきっかけとして想定しています。運動の継続を保証するのではなく、運動を始めるハードルを下げることを目指します。

## 既存サービス・競合調査

### TinyWin - Gentle Habit Tracker

- **URL：** [App Store](https://apps.apple.com/us/app/tinywin-gentle-habit-tracker/id6787733326)
- **できること：**
  - 習慣を記録し、実行した日を振り返る
  - 「Just Start」モードで、習慣を始めるための小さな行動を設定する
  - 既存の習慣に新しい習慣を結びつける
  - 実行後に気分や感想を記録する
  - ホーム画面のウィジェットから習慣を確認・記録する
  - 連続記録が途切れても、それまでの達成を失敗として扱わない設計

### それでも作りたい理由

TinyWinには、習慣を小さく始めたり、できなかった日を過度に責めないようにしたりする仕組みがあります。「ちょい動き」も行動のハードルを下げる点で共通しています。

一方、このアプリでは運動に対象を絞り、運動したいと思ったときに内容を考える負担を減らすことに焦点を当てます。アプリから小さな運動タスクを提案し、ユーザー自身もタスクを登録できるようにすることで、「何をすればよいかわからず、結局何もしない」という状況を減らすことを目指します。

### 差別化する体験

このアプリは、**運動したい気持ちはあるが、疲れて帰宅した後に何をするか決められない人**が、**考え込まずに小さな運動を始める瞬間**を助けるアプリと考えてます。

運動内容はアプリが提案、スクワット3回や足踏み（膝を腰まで上げる）を5回など、まずは体を動かすことへのハードルを極力さげ、運動することに対する抵抗を小さくすことが目的。

## 提供したい価値

- **行動の変化：** 運動内容を考え込まず、小さなタスクから始められる
- **気持ちの変化：** 「運動は大変」という負担感を少し減らせる
- **考え方の変化：** 運動を、まとまった時間をかけて行うものだけでなく、小さく始められる行動として捉えられる

**このサービスは、運動を始めたいが帰宅後に行動へ移せない人が、小さな運動タスクから始められるようにするサービスです。**

## MVPで実現すること

- ユーザー登録・ログイン・ログアウト
- ログイン中のユーザー自身のタスクと達成記録だけを表示・管理する
- 運動タスクを10個程度、あらかじめ用意する
- 用意したタスクから、日替わりでおすすめを1つ表示する
- 「別の候補を見る」から、用意されたタスクを選び直せる
- ユーザーがタスク名を入力して、自分のタスクを登録できる
- タスクごとに「できた」を記録する
- 今日の達成状況と、日付・タスク名による過去の履歴を表示する
- 連続日数ではなく、今週の達成回数を表示する


### MVPでは扱わないこと

- 水分補給など、運動以外の健康習慣
- 体調や気分に応じたタスクの自動調整
- 通知、SNS共有、詳細なグラフ
- カレンダー形式の履歴表示

## 懸念点と対策

### 提案されたタスクがユーザーに合わない

- **懸念：** 提案されたタスクが簡単すぎる、または難しすぎると感じ、利用されなくなる可能性がある
- **対策：** 別の候補を選べるようにし、ユーザー自身がタスクを登録できるようにする

### タスクが小さすぎて価値を感じられない

- **懸念：** 「足踏みだけでよいのか」と疑問に思われる可能性がある
- **対策：** 運動効果を約束するのではなく、「運動を始めるきっかけを作る小さなタスク」として説明する

## 技術スタック

### 使用予定の技術

本アプリはRuby 3.4系とRuby on Rails 8.1系を候補として開発する予定です。画面はRails標準テンプレートとHotwireを中心に実装し、スタイルには通常のCSSを使用します。データベースにはPostgreSQL 14.x〜16.xを採用し、Renderへのデプロイを目指します。MVPではDockerを使わず、環境構築の範囲を抑えて主要機能の実装を優先します。

テストにはRails標準のMinitestを使う予定です。実装開始前にRuby・RailsのバージョンとRenderの実行条件を確認し、使用するバージョンを固定します。

### 技術選定の比較検討

現在学習しているRailsを軸に、MVPを完成させるための技術を選びます。

| 項目 | 採用予定 | 選定理由・比較 |
| --- | --- | --- |
| 言語・フレームワーク | Ruby 3.4系 / Rails 8.1系 | Railsを中心に画面・ルーティング・DB連携を実装する。学習中のRails 7系との違いは事前に確認する |
| 画面 | Rails標準テンプレート + Hotwire | Rails内で画面を実装し、構成をシンプルに保つ。Reactも学習中だが、今回は実装範囲を絞り、必要性があれば本リリース以降に検討する |
| スタイル | 通常のCSS | Tailwind CSSの設定・学習よりもMVPの機能開発を優先する |
| データベース | PostgreSQL 14.x〜16.x | SQLの学習経験を活かし、タスクや達成記録を管理する |
| デプロイ | Render | アプリを公開し、PostgreSQLと連携した動作を確認する |
| コンテナ | MVPではDockerを使わない | 環境構築の作業を抑えて機能実装に集中する。必要性が出た場合に再検討する |

- **使用予定ライブラリ：** Hotwire（Turbo / Stimulus）。その他は必要に応じて選定する
- **今回チャレンジしたい点：** Railsでタスク登録・達成記録・履歴表示を実装する
- **不安な点：** 学習中の環境とのバージョン差、DB設計、1ヶ月以内の実装とデプロイ

### キャッチアップ不足の懸念

バージョン間の違いやRenderへのデプロイに想定以上の時間がかかる可能性があります。また、Rails 8.1系のサポート状況は実装開始時に公式情報を再確認します。

使用する技術やライブラリを必要最小限にし、まずはMVPの機能を優先します。Docker、通知、カレンダーUI、複雑なグラフなどはMVP完成後に必要性を検討。
